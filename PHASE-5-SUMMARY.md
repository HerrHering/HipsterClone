# Phase 5 — Hosting it for a real game night (Docker + Tailscale Funnel)

Phases 1–4 built and polished the game itself; nothing about game logic
changed here. This phase is pure "operations": packaging the app so it
runs the same way on any machine (Docker), and making it reachable by
friends over the public internet for free, without a router or a
domain name (Tailscale Funnel).

You said you're new to Docker and have only used a plain Tailscale
network ("tailnet") before, not Funnel — so this summary spends more
time explaining the *concepts*, not just what files got added.

---

## 1. What Docker actually is

Without Docker, "run this app on another computer" means: install the
exact right Node version, install `ffmpeg`, install a recent enough
`yt-dlp`, get all the folder paths right, hope nothing on that machine
conflicts with something else already installed there. Every one of
those steps is a place where "works on my machine" can quietly stop
being true on a different machine.

Docker's idea: describe *once*, in a text file (the `Dockerfile`),
exactly what a working machine for this app looks like — starting from
a known, fixed operating-system snapshot, then a fixed list of "install
this, copy that, run this command." Docker then builds that description
into an **image**: a single, self-contained, frozen file that has
*everything* the app needs already inside it — Node, ffmpeg, yt-dlp,
your compiled code, all of it. An image is like a recipe that's already
been cooked and vacuum-sealed.

A **container** is just a running instance of an image — the same
relationship a class has to an object, if that's a more familiar
analogy. You can start, stop, and throw away containers freely; the
image itself never changes once built. This is why Docker solves
"works on my machine": the *whole* machine-shape (OS + tools + code) is
inside the image, so if it works in a container on your dev laptop, it
works identically in a container on the second desktop — nothing about
the *host* machine's own installed software matters anymore.

Two other pieces of vocabulary you'll see below:
- **Layers** — a Dockerfile is a sequence of steps, and Docker caches
  the result of each one. If you change one line near the bottom of the
  file and rebuild, Docker reuses its cached results for every step
  above the one that changed, instead of redoing everything from
  scratch. This is why the Dockerfile below deliberately copies
  `package.json` files and runs `npm ci` *before* copying the rest of
  the source — editing a `.tsx` file shouldn't force a slow
  from-scratch `npm ci` every time.
- **Volumes** — a container's own filesystem is thrown away with the
  container by default. A volume is an explicit exception: "this one
  folder should actually live on the real host disk, not disappear
  when the container does." We use this for the downloaded songs (so
  you don't re-download your whole catalog every time you restart the
  server) and for the YouTube cookies file (so it's a real file you
  manage, not something baked into the image).

## 2. The `Dockerfile`, section by section

This project's [`Dockerfile`](Dockerfile) has two stages — think of it
as two separate recipes stapled together, where the second one gets to
reach back and grab specific finished dishes from the first.

### Stage 1: `build`

```dockerfile
FROM node:22-slim AS build
WORKDIR /app

COPY package.json package-lock.json ./
COPY packages/shared/package.json packages/shared/package.json
COPY apps/api/package.json apps/api/package.json
COPY apps/web/package.json apps/web/package.json
COPY tools/scraper/package.json tools/scraper/package.json
RUN npm ci

COPY . .
RUN npm run build
```

- `FROM node:22-slim AS build` — start from an official, pre-built
  image that already has Node 22 installed on a minimal Debian Linux.
  `AS build` just gives this stage a name, so stage 2 can refer back to
  it later.
- `WORKDIR /app` — every command after this runs as if you'd `cd`ed
  into `/app` inside the image. This is why paths in the rest of the
  file (like `packages/shared/package.json`) are written relative to
  the repo root — they mirror this project's real folder layout,
  one-to-one, inside the image.
- The five `COPY` lines copy in *only* the `package.json` files first
  (this is the layer-caching trick from §1) — `npm ci` (a clean,
  lockfile-exact install) then downloads every dependency.
- `COPY . .` — now copy in literally everything else: all the real
  source code, including `apps/web/public/manifest.json`. That file is
  gitignored (it's regenerated by the scraper, not checked into git),
  but Docker doesn't care about git — it just copies whatever's really
  sitting on disk when you run `docker build`. That's why step 2 of the
  setup guide below is "make sure it already exists before building."
- `RUN npm run build` — runs this repo's own root build script, which
  compiles `packages/shared`, then builds `apps/web` (Vite), then
  compiles `apps/api` (`tsc`). Same command you'd run locally.

### Stage 2: the runtime image

```dockerfile
FROM node:22-slim
WORKDIR /app

RUN apt-get update \
  && apt-get install -y --no-install-recommends ffmpeg python3 python3-venv \
  && rm -rf /var/lib/apt/lists/* \
  && python3 -m venv /app/.venv \
  && /app/.venv/bin/pip install --no-cache-dir -U yt-dlp

COPY package.json package-lock.json ./
COPY packages/shared/package.json packages/shared/package.json
COPY apps/api/package.json apps/api/package.json
RUN npm ci --omit=dev --workspace=@hipster-clone/api --workspace=@hipster-clone/shared

COPY --from=build /app/packages/shared/dist packages/shared/dist
COPY --from=build /app/apps/api/dist apps/api/dist
COPY --from=build /app/apps/web/dist apps/web/dist
COPY --from=build /app/apps/web/public/manifest.json apps/web/public/manifest.json

ENV NODE_ENV=production
EXPOSE 5174
CMD ["node", "apps/api/dist/server.js"]
```

This starts a **second, brand-new** `node:22-slim` image — the `build`
stage above is thrown away entirely, *except* for the specific files we
explicitly reach back and grab with `COPY --from=build`. This is the
whole point of a multi-stage build: the final image never contains
TypeScript source, `devDependencies`, or build tools — just the
compiled JavaScript and exactly the runtime tools it needs. Smaller
image, smaller attack surface, faster to transfer to the second
desktop.

- `apt-get install ... ffmpeg python3 python3-venv` — `ffmpeg` is what
  yt-dlp uses to extract/convert audio; `python3`/`python3-venv` let us
  install yt-dlp itself (it's a Python program, not a Node one).

- `python3 -m venv /app/.venv && .../pip install -U yt-dlp` is worth
  unpacking properly, since it's the same recipe you'd run by hand on
  *any* machine (not just inside Docker) to get a working, up-to-date
  yt-dlp — and it's not arbitrary here: `apps/api/src/downloadClip.ts`
  already specifically looks for a binary at `.venv/bin/yt-dlp`
  relative to the repo root before falling back to a plain `yt-dlp` on
  PATH, so this Dockerfile line exists purely to satisfy that same
  lookup.

  - `python3 -m venv /app/.venv` creates a **virtual environment**: an
    isolated folder with its own private copy of Python's package
    installer, so installing something into it can never clash with —
    or get clobbered by — whatever Python packages the rest of the
    system has. `/app/.venv/bin/pip` and `/app/.venv/bin/yt-dlp` end up
    living *inside* that folder.
  - `/app/.venv/bin/pip install --no-cache-dir -U yt-dlp` — `pip` is
    Python's package installer (the equivalent of `npm install`, but
    for Python). `-U` means "upgrade to the latest version" rather than
    whatever might already be around. This matters specifically for
    yt-dlp: YouTube frequently changes the JavaScript challenge it uses
    to detect bots, and yt-dlp ships near-constant updates to keep up —
    an old version (like whatever a Linux distro's own package manager
    might ship, possibly months stale) can simply stop working. `-U`
    against a fresh venv guarantees whatever's newest at build time.
  - **You can run this exact same recipe yourself**, outside Docker, on
    any machine with Python installed, any time a local `yt-dlp` starts
    failing on real downloads:
    ```
    python3 -m venv .venv
    .venv/bin/pip install -U yt-dlp
    ```
    `downloadClip.ts` will then automatically prefer that fresh copy
    over whatever's on PATH — no code or config change needed, it's
    already looking for exactly this folder.
- The second `npm ci --omit=dev --workspace=...` installs *only*
  production dependencies for *only* the two workspaces this image
  actually runs (`api` and `shared`) — `apps/web` and `tools/scraper`
  never even get their `node_modules` installed here, since nothing in
  the running server needs them (the web app is just static files by
  this point).
- The four `COPY --from=build` lines pull the *compiled* output out of
  stage 1 — this is the only place stage 1's work actually gets used.
- `EXPOSE 5174` is documentation (which port this container listens
  on) — it doesn't actually publish anything by itself; that's
  `docker-compose.yml`'s job, next.
- `CMD [...]` is what runs when the container starts — the exact same
  `node apps/api/dist/server.js` you could run locally after a build.

## 3. `docker-compose.yml`

```yaml
services:
  api:
    build: .
    ports:
      - "5174:5174"
    environment:
      NODE_ENV: production
      PORT: "5174"
      YTDLP_COOKIES_FILE: /app/cookies.txt
    volumes:
      - ./cookies.txt:/app/cookies.txt
      - ./apps/api/data/cache:/app/apps/api/data/cache
    restart: unless-stopped
```

Compose is a small orchestration layer on top of plain Docker — instead
of a long `docker run --port ... --env ... --volume ...` command typed
by hand, it's all written down once and started with `docker compose up`.

- `build: .` — build the `Dockerfile` sitting in this same folder.
- `ports: ["5174:5174"]` — the format is `"host:container"`. This
  publishes the container's port 5174 as port 5174 on the real desktop
  itself, which is what lets `tailscale funnel` (step 6 below) point at
  `localhost:5174` and find it.
- `environment:` sets the same env vars you'd otherwise export by hand
  — `YTDLP_COOKIES_FILE` is the one from Part A that tells
  `downloadClip.ts` to use a mounted cookie file instead of trying (and
  failing) to read a real browser's profile.
- `volumes:` — the `host-path:container-path` pairs from §1. The
  cookies mount is deliberately **not** `:ro`: yt-dlp's `--cookies` flag
  treats the file as a live jar, not just an input — it rewrites it
  (rotated/refreshed cookies) every time it exits, even after a
  successful download. A read-only mount here makes that final write
  fail with "Read-only file system", which crashes yt-dlp on every
  single run and makes `downloadClip.ts` report every song as failed —
  a real bug hit and fixed after Phase 5's initial `:ro` mount turned
  out to be incompatible with how yt-dlp actually uses this file.
- `restart: unless-stopped` — if the container crashes, or the desktop
  reboots, Docker starts it again automatically, without you needing to
  SSH in and run anything by hand.

## 4. Tailscale Funnel — the part you haven't used before

You already know a **tailnet**: your own private network connecting
your own logged-in devices over WireGuard, where nothing on it is
reachable by anyone outside it.

**Funnel** is a narrow, deliberate exception to that: you pick one
local port on one device, and Funnel publishes *just that* to the
public internet over real HTTPS — Tailscale automatically issues a
valid TLS certificate for it. Nothing else about your tailnet, your
other devices, or your home network becomes reachable; it's scoped to
exactly the port you turn it on for.

**How it avoids needing a router or public IP at all:** your desktop
makes an *outbound* connection out to Tailscale's own relay
infrastructure (outbound connections work through almost any home
router/NAT with zero configuration). Tailscale's relay keeps that
connection open and uses it as a two-way pipe — the public internet
talks to *Tailscale's* address, which forwards the traffic down that
pipe to your desktop, and sends the response back the same way. Your
home router never has anything "open" to the internet at all.

**Do your friends need a Tailscale account? No.** This was worth
double-checking against Tailscale's current docs rather than assuming:
Funnel visitors hit a normal public HTTPS URL in any ordinary browser —
no Tailscale client, no login, nothing installed. The "6 free users"
limit on Tailscale's free plan only counts people *you* invite into
*your own* tailnet (e.g. a family member's laptop) — it has nothing to
do with how many strangers can open a Funnel link, exactly like a
regular website has no such limit either.

**Security, honestly:** your home IP is never exposed, and the
connection is properly encrypted end-to-end. But Funnel is a pipe, not
a firewall for the app itself — whatever you expose is genuinely
public. This game has no login, just 4-letter room codes, so anyone who
finds your URL and guesses/knows a code could join or poke at that
room. For a free, low-stakes party game with no accounts or personal
data, that's a perfectly reasonable trade-off — just know Funnel isn't
adding access control on its own.

**Capacity:** Tailscale doesn't publish an exact bandwidth number for
Funnel, but it's documented as comfortably handling things like 4K
video streaming — this app (small JSON polling + a handful of few-MB
mp3 clips) is far lighter than that.

## 5. Setting the website's name

The full address is `https://<machine-name>.<tailnet-name>.ts.net` —
two independently renameable pieces:

- **The machine name** (the first part) — rename the second desktop in
  Tailscale's admin console (Machines page → click the device → rename)
  or from its own terminal:
  ```
  sudo tailscale set --hostname=hipster
  ```
  This alone gets you e.g. `https://hipster.<whatever-tailnet>.ts.net`.
- **The tailnet name** (the second part) — by default it's a random
  string like `tail3f9a2.ts.net`. In the admin console's DNS page,
  "Rename tailnet" lets you pick from a set of freshly-generated
  memorable options (like `cat-crocodile.ts.net`) instead — free, no
  domain purchase, just not a string you type yourself (Tailscale
  generates the options; you pick or re-roll).

Combined, something like `https://hipster.cat-crocodile.ts.net` is a
genuinely free, stable, fairly memorable address — as good as it gets
without actually owning a domain.

## 6. Step-by-step: get it running on the second desktop

**On this dev machine, once:**

1. Make sure `apps/web/public/manifest.json` exists (run `npm run
   scrape` if it doesn't — the Docker build needs it).
2. Export YouTube cookies from your browser. **Why this is needed at
   all:** YouTube requires proof a request isn't a bot, and the way
   `downloadClip.ts` normally satisfies that locally is
   `--cookies-from-browser firefox` — it reads the cookies straight out
   of your *actual, currently logged-in* Firefox profile on this
   machine. The second desktop's container has no such profile (it's
   headless, and containers don't have a browser at all), so instead we
   export those same cookies to a plain text file once, here, and hand
   that file to the container instead.

   The easiest way to get that file is to let yt-dlp itself do the
   export — it already knows how to read a real browser's cookie
   database, so no separate browser extension is needed:
   ```
   yt-dlp --js-runtimes node --remote-components ejs:github --cookies-from-browser firefox --cookies cookies.txt --skip-download \
     "https://www.youtube.com/watch?v=dQw4w9WgXcQ"
   ```
   What each piece does: `--cookies-from-browser firefox` is the same
   flag `downloadClip.ts` already uses — reads Firefox's real cookie
   jar. `--cookies cookies.txt` tells yt-dlp to *write out* whatever
   cookies it finds into that file (in the plain-text "Netscape" format
   yt-dlp itself expects to read back later) instead of only using them
   in-memory for this one run. `--skip-download` means "just do the
   cookie extraction, don't actually fetch this video" — the URL is
   only there because the command needs *some* YouTube page to visit to
   trigger the export; any real video URL works. `cookies.txt` appears
   in your repo root when this finishes.

   If you use a different browser day-to-day, swap `firefox` for
   `chrome`, `chromium`, `edge`, `brave`, `opera`, `vivaldi`, or
   `safari` — yt-dlp supports the same flag for all of them. One common
   gotcha: some browsers lock their cookie database file while running,
   so if the export fails, fully close the browser first and try again.

   Treat the resulting `cookies.txt` like a password — it's real,
   working login credentials for your YouTube session. It's already
   covered by `.gitignore`, but don't paste its contents anywhere public
   either, and re-export a fresh one if it ever stops working (cookies
   do eventually expire).
3. Copy the whole repo to the second desktop (`git clone` there, then
   copy over the two gitignored files it needs: `cookies.txt` and
   `apps/web/public/manifest.json` — e.g. via `scp`, a USB drive, or a
   shared network folder).

**On the second desktop — what actually needs installing there, and
what doesn't:**

This is worth being explicit about, since it's easy to assume — coming
from "normally I'd `npm install` everything" — that Node/npm/yt-dlp/
ffmpeg all need setting up on this machine too. They don't. That's
the whole point of §1: everything the app needs to *run* (Node, ffmpeg,
yt-dlp, your compiled code) lives inside the Docker image itself, built
automatically the first time you run `docker compose up --build` — the
`npm ci`/`npm run build` from the Dockerfile happen *inside* that build,
using the image's own Node, completely independent of whatever is or
isn't installed on this machine's actual OS.

So the second desktop only needs three things installed directly:
**git** (just to get the code onto the machine — skip this if you'd
rather transfer files by `scp`/USB instead), **Docker**, and
**Tailscale**. Nothing else.

4. Check whether `git` is already there, install it if not (Debian/
   Ubuntu; swap `apt` for your distro's package manager if it's
   something else):
   ```
   git --version || sudo apt install -y git
   ```
   Then clone the repo (or skip this and just copy the folder over by
   `scp`/USB if you'd rather not set up git access on this machine at
   all):
   ```
   git clone <your-repo-url> ~/HipsterClone
   cd ~/HipsterClone
   ```
5. Install Docker:
   ```
   curl -fsSL https://get.docker.com | sh
   ```
   This one script installs everything needed — the Docker engine, the
   CLI, and the `docker compose` plugin together — so there's no
   separate "now install Compose" step. Confirm both landed:
   ```
   docker --version
   docker compose version
   ```
   One common first-run snag: fresh installs typically only let `root`
   run `docker` commands, so a plain `docker compose up` as yourself
   fails with a permission error on `/var/run/docker.sock`. Either
   prefix every docker command with `sudo` from here on, or (nicer) add
   your user to the `docker` group once and log out/back in (or run
   `newgrp docker` to pick it up in your current shell without
   logging out):
   ```
   sudo usermod -aG docker $USER
   newgrp docker
   ```
6. Build and start the game server:
   ```
   docker compose up -d --build
   ```
   `-d` runs it in the background. Check it's healthy:
   ```
   docker compose logs -f       # watch live logs, Ctrl+C to stop watching
   curl http://localhost:5174/api/cached-ids   # should print [] or a list, not an error
   ```
7. Install Tailscale and join your tailnet:
   ```
   curl -fsSL https://tailscale.com/install.sh | sh
   sudo tailscale up
   ```
   This opens a link to log in with your Tailscale account (the same
   one, if you want to manage things from this dev machine too).
8. (Optional, once) Rename the machine so the URL reads nicely — see
   §5 above.
9. Turn on Funnel for the game's port:
   ```
   sudo tailscale funnel 5174
   ```
   The first time, it prints a link to approve enabling HTTPS certs +
   Funnel for your tailnet — open it, approve. It then prints your
   public address:
   ```
   Available on the internet:
   https://hipster.cat-crocodile.ts.net
   |-- / proxy http://127.0.0.1:5174
   ```

That URL is what you send your friends. Any phone, any network, no
Tailscale install needed on their end.

## 7. Optional: a real Node dev setup on the second desktop too

Everything above is enough to just *run* the game. If you also want to
make quick fixes directly on the second desktop (instead of always
editing here and copying files over — reasonable, since that copying
step is exactly the kind of manual, error-prone busywork Docker is
otherwise helping you avoid), you need Node/npm — and, if you also want
the scraper to work there, `yt-dlp` too (it shells out to it for
YouTube search, the same as `downloadClip.ts` does for downloads — see
`tools/scraper/src/resolveSource.ts`). `ffmpeg` only matters if you'll
also run `npm run dev` directly on this machine (outside
`docker compose`) and want song playback to work in that dev session;
skip it if you'll only ever edit code and test through the real
`docker compose` stack.

Two ways to get there — pick whichever fits how "permanent" you want
this to be:

### Option A — a reusable dev container (nothing installed on the host OS)

Keeps the second desktop itself completely clean — Node/yt-dlp only
ever exist inside a container, never touch the real OS. Build a small
dev image once:

```dockerfile
# Dockerfile.dev — for interactive development only, never used to
# actually serve the game (that's the plain Dockerfile + docker-compose.yml).
FROM node:22-slim
WORKDIR /app
RUN apt-get update \
  && apt-get install -y --no-install-recommends ffmpeg python3 python3-venv git \
  && rm -rf /var/lib/apt/lists/* \
  && python3 -m venv /app/.venv \
  && /app/.venv/bin/pip install --no-cache-dir -U yt-dlp
CMD ["bash"]
```
```
docker build -f Dockerfile.dev -t hipster-dev .
```

Then, any time you want to work on the code, drop into a shell inside
it with your real repo folder mounted in live:

```
docker run --rm -it -v "$PWD":/app -p 5173:5173 -p 5174:5174 hipster-dev
```

Inside that shell you have `npm`, `node`, and `yt-dlp` exactly like a
normal dev machine — `npm install`, `npm run dev`, `npm run scrape`,
all work. `--rm` deletes the *container* the moment you exit, but since
your code lives in the mounted folder (not inside the container), and
`node_modules` gets written into that same mounted folder, nothing is
lost between sessions — next time you run the same command, your files
and installed packages are still there; only the container's
throwaway OS-level state resets. One gotcha: Vite's dev server only
listens on `localhost` by default, so it won't be reachable through
`-p 5173:5173` from outside the container unless you start it with
`npm run dev -w apps/web -- --host` instead of the root `npm run dev`.

### Option B — install Node (+ yt-dlp) directly on the desktop

Simpler day-to-day (no `docker run` wrapper to remember), at the cost
of Node living permanently on that machine, same as this one:

```
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt-get install -y nodejs ffmpeg python3 python3-venv
```
(The NodeSource script sets up an apt source for Node 22, matching the
version this project already targets — `nodejs` there also brings
`npm` with it.) Then, in the repo folder:
```
python3 -m venv .venv
.venv/bin/pip install -U yt-dlp
npm install
```
From here, `npm run dev`, `npm run scrape`, and `npm run build` all
work exactly like they do on this machine.

Either way, the production game itself keeps running through
`docker compose` — a dev setup (A or B) is purely for editing/testing;
it doesn't replace or interfere with the real running container.

---

**Day-to-day after that:** the server survives desktop reboots on its
own (`restart: unless-stopped` in `docker-compose.yml`, and Tailscale
itself starts on boot too). To ship a code update: either edit directly
on the second desktop now (§7) and run `docker compose up -d --build`
right there, or keep editing here and copy the changed files over first
— either way, cached songs in `apps/api/data/cache` survive the
rebuild.

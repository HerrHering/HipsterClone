# Phase 2 — Walkthrough

Phase 1 proved playback works, but every song needed a human to run one `yt-dlp` command by hand. Phase 2 automates that — you now only type `artist, title, year` into a spreadsheet, and the actual YouTube link is found automatically. Downloading the audio itself becomes *lazy*: nothing is fetched until a browser actually asks to play that song, and it's kept ("cached") on disk after that until you delete it.

This split — resolve a link ahead of time, download the bytes on demand — is why Phase 2 introduces a real backend server for the first time. Read this top to bottom once, then use **"How to add songs"** at the end as your day-to-day reference.

## Part 2: `resolveSource.ts` — searching YouTube without downloading anything

`yt-dlp` isn't only a downloader — it can also *search*:

```bash
yt-dlp --dump-json --no-download --flat-playlist "ytsearch5:Queen Bohemian Rhapsody"
```

`ytsearch5:<query>` is a special "URL" yt-dlp understands as "search YouTube for this text, treat the top 5 results as a playlist." `--no-download --flat-playlist` means "just tell me about each result (title, channel, duration, video id) — don't fetch anything." This is fast and needs no login, which is why resolution (this step) can safely run as part of the ordinary `npm run scrape` build step, while actual downloading (Part 4) can't.

### Never build a shell string from user input

```ts
const { stdout } = await execFileAsync(
  YTDLP_BIN,
  ["--dump-json", "--no-download", "--flat-playlist", query],
  { maxBuffer: 10 * 1024 * 1024 },
);
```

`execFile` (from Node's built-in `child_process`, wrapped with `promisify` so it returns a `Promise` instead of taking a callback) runs a program directly with an argument **array** — there is no shell involved at all. Compare that to `exec("yt-dlp " + query)`, which would hand the whole string to `/bin/sh` — if `query` ever contained something like `; rm -rf ~`, a shell would happily execute it. Since `query` is built from artist/title text you typed into a CSV, it's "trusted" today, but the habit matters: `execFile` with an argument array is simply never vulnerable to this class of bug, so there's no need to reason about escaping at all.

### Picking which `yt-dlp` binary to run

```ts
const venvYtDlp = resolve(repoRoot, ".venv/bin/yt-dlp");
const YTDLP_BIN = existsSync(venvYtDlp) ? venvYtDlp : "yt-dlp";
```

While building this, the system-installed `yt-dlp` (`/usr/bin/yt-dlp`, version `2024.04.09`) turned out to be too old — YouTube now requires solving a small JS "signature challenge" before it'll hand over a download URL, and support for that only landed in newer `yt-dlp` releases. This project's `.venv/` (a Python virtual environment — an isolated folder of Python packages so they don't clash with your system's Python) has a much newer `yt-dlp` (`2026.08.19`) installed via `pip`. Both `resolveSource.ts` and `downloadClip.ts` prefer that binary if it exists, falling back to whatever `yt-dlp` resolves to on `$PATH` otherwise — so it still works on a machine where the system install is already new enough.

### Scoring candidates

`yt-dlp` doesn't know which of its 5 results is "the real song" — it just ranks by YouTube's own relevance. `resolveSource` scores each candidate itself, as a weighted sum of four small, independently-named sub-scores:

```ts
const score =
  titleOverlapScore(targetWords, candidateWords) * TITLE_OVERLAP_WEIGHT +
  artistMentionedScore(normalizedArtist, normalizedChannel, normalizedCandidateTitle) *
    ARTIST_MENTIONED_WEIGHT +
  durationPlausibleScore(candidate.duration ?? 0) * DURATION_PLAUSIBLE_WEIGHT -
  nonOriginalPenalty(normalizedCandidateTitle);

return Math.max(0, score);
```

- **`titleOverlapScore`** (weight `0.6`, the biggest factor) — what fraction of the target title's significant words (after stripping filler like "official", "video", "the") also appear in the candidate's title.
- **`artistMentionedScore`** (weight `0.25`) — 1 if the artist's name shows up in the candidate's channel/uploader name or in its title, else 0. Catches the common case where an official artist channel uploaded the track.
- **`durationPlausibleScore`** (weight `0.15`) — 1 if the candidate is between 60 seconds and 15 minutes, else 0. Filters out 30-second teasers and multi-hour "full album" uploads without needing to understand what the video actually contains.
- **`nonOriginalPenalty`** (flat `0.3`, subtracted rather than weighted) — applied if the title contains words like "cover", "live", "remix", "karaoke" — a heuristic for "probably not the canonical studio version."

Each sub-score is a small standalone function that takes already-normalized strings and returns a plain number — easy to read (and to unit-test in isolation) without needing to trace through the whole scoring pipeline. The composing function, `scoreCandidate`, does exactly one other thing worth calling out:

```ts
// Normalize each input exactly once, up front, and hand the results to
// the sub-scores below — candidate.title in particular used to get
// re-normalized three separate times (once per sub-score that needed it).
const normalizedCandidateTitle = normalize(candidate.title);
```

An earlier version of this function called `normalize(candidate.title)` three separate times — once to build the word-overlap set, once for the artist-mentioned-in-title check, once for the cover/live penalty check — each re-running the same handful of regex passes over the same string for no reason. Normalizing once up front and threading the result into each sub-score removed the redundant work and, as a side effect, made each sub-score's signature honestly reflect what it needs (already-normalized text in, a number out) rather than re-deriving its own inputs from raw strings.

The candidates are sorted by this score and the **top one is always used** — per your explicit direction, the pipeline never stops to ask a human to pick from a list. But:

```ts
if (best.score < CONFIDENCE_WARN_THRESHOLD) {
  console.warn(`resolveSource: low-confidence match (${best.score.toFixed(2)}) ...`);
}
```

A low score still gets used, but logs a warning during `npm run scrape` so you can notice a bad match later. If the automated guess is wrong for some song, Part 3's local-file override lets you fix just that one song by hand, without touching anything else.

**Known limitation:** this is a heuristic, not a guarantee. It can still pick a cover, a lyric video with an unusual title, or a fan reupload if that's genuinely the closest-scoring result. For a party game, a wrong backing track is a minor annoyance, easily fixed via the override below — not a correctness bug worth building a full manual-review UI for.

## Part 3: `index.ts` — one id-derivation rule, no special cases

```ts
const id = slugify(`${row.title}-${row.artist}-${row.year}`);
```

`slugify` (new, in `slug.ts`) lowercases the text and replaces every run of non-alphanumeric characters with a single hyphen — e.g. `"Bohemian Rhapsody-Queen-1975"` → `"bohemian-rhapsody-queen-1975"`. Combining title *and* artist *and* year makes it essentially impossible for two different rows to collide, which is deliberate: earlier drafts of this considered a fallback chain (try title alone, then title+artist, then a numeric suffix) for when two songs shared a title, but that adds edge cases for a problem that combining all three fields already prevents outright. One rule, no exceptions to remember.

For each row, in order:

```ts
if (existsSync(localAudioPath)) {
  entries.push({ ..., audio: { kind: "local-file", ref: `/audio/${id}.mp3` } });
  continue;
}
```

**1. Local file wins if present.** This is unchanged from Phase 1's own check — and it doubles as your manual override. If the automated resolver ever picks the wrong video for some song, you don't need to edit any code: just drop a corrected mp3 at `apps/web/public/audio/<id>.mp3` (matching the id `slugify` would derive for that row) and the resolver is skipped entirely for that song, same as it always was for the two hand-downloaded Phase 1 songs.

```ts
const previous = previousEntriesById.get(id);
if (previous && previous.audio.kind === "embedded-link") {
  entries.push(previous);
  continue;
}
```

**2. Otherwise, reuse a previous resolution if one exists.** `index.ts` now reads the manifest.json from the *previous* run (if any) before writing the new one, so a song already resolved on an earlier `npm run scrape` isn't searched again. Without this, adding one new row to a 50-song catalog would re-run 50 YouTube searches every time — wasteful, and edges toward rate-limiting. Because ids are derived from `title-artist-year`, this cache-lookup is naturally invalidated if you ever *change* one of those fields for a song (it becomes a "new" id and gets re-resolved) — a fresh problem gets a fresh answer, without needing any explicit invalidation logic.

```ts
const resolved = await resolveSource(row.title, row.artist);
if (!resolved) {
  console.warn(`skipping "${row.title}" by "${row.artist}": could not resolve a source`);
  continue;
}
entries.push({ ..., audio: { kind: "embedded-link", ref: resolved.videoId, durationSec: resolved.durationSec } });
```

**3. Otherwise, resolve it now.** Note the entry's `audio.ref` here is a YouTube **video id** (11 characters, e.g. `"fJ9rUzIMcZQ"`), not a file path — nothing has been downloaded. `buildManifest.ts` is completely unchanged from Phase 1; it doesn't know or care whether an entry is `local-file` or `embedded-link`, it just writes whatever entries it's given.

This is also why `tools/scraper` no longer has a `downloadClip.ts` — this script never downloads audio anymore, only text metadata (search results). The one that actually downloads moved to `apps/api`, next.

## Part 4: `apps/api` — the on-demand download-and-cache server

A browser can `fetch()` URLs, but it cannot run an external program like `yt-dlp`. So the moment a song's audio needs to actually be *fetched* (rather than just referenced), something with real OS process access has to do it — which means, for the first time in this project, an always-running server process, not just a static file host.

### `downloadClip.ts` — the real download, with two YouTube-imposed requirements discovered by testing

The naive command,

```bash
yt-dlp -x --audio-format mp3 --download-sections "*0:00-5:00" -o out.%(ext)s "https://www.youtube.com/watch?v=<id>"
```

fails outright on this machine with `ERROR: Sign in to confirm you're not a bot`. Two things fix it, both confirmed by hand before writing any code:

1. **`--js-runtimes node --remote-components ejs:github`** — lets `yt-dlp` solve YouTube's JS signature challenge itself (using Node, which this project already depends on, to execute the challenge script; `ejs:github` fetches the small interpreter component it needs from GitHub on first use).
2. **`--cookies-from-browser <browser>`** — borrows session cookies from a real, already-logged-in browser on the machine, which is what actually satisfies the "not a bot" check.

Flag 2 is inherently machine-specific — your friends won't all use Firefox. So it's read from an environment variable rather than hardcoded:

```ts
const cookiesBrowser = process.env.YTDLP_COOKIES_BROWSER ?? "firefox";
const cookieArgs =
  cookiesBrowser && cookiesBrowser !== "none"
    ? ["--cookies-from-browser", cookiesBrowser]
    : [];
```

Whoever runs `apps/api` sets `YTDLP_COOKIES_BROWSER=chrome` (or `edge`, `brave`, etc. — anything `yt-dlp --cookies-from-browser` supports) if Firefox isn't their browser, or `=none` if downloads work without it on their machine/network. Defaulting to `"firefox"` matches this project's own dev setup rather than guessing at something more "neutral" — there's no universally-correct default here, only a documented, overridable one.

The rest mirrors Phase 1's manual command exactly, just built as an argument array instead of typed by hand — including the same `--download-sections "*0:00-5:00"` safety cap, and the same video-id-shape check (`^[\w-]{11}$`) before it's ever used to build a URL, defense-in-depth against a malformed id ending up somewhere unexpected even though it always comes from `resolveSource`'s own output, not directly from user input.

### `cache.ts` — the `ensureCached` seam

```ts
export async function ensureCached(id: string): Promise<string | null> {
  if (isCached(id)) {
    return cachedFilePath(id);
  }
  const song = await findSong(id);
  if (!song || song.audio.kind !== "embedded-link") {
    return null;
  }
  const result = await downloadClip(id, song.audio.ref, cacheDir);
  return result?.filePath ?? null;
}
```

This one function is the entire "start empty, download on demand, cache after that" behavior: check disk first, only call out to `yt-dlp` on a miss. It's written to be **idempotent** — calling it five times in a row for the same id does the real work once and then just returns the cached path — which is exactly the property a future "prefetch the next song" feature needs: it could call this same function *before* the current song finishes playing, entirely speculatively, with zero risk of double-downloading or racing the eventual real playback request. That trigger doesn't exist yet (out of scope for this phase), but the seam it would call into already does — see the `/prefetch` route below, which exists and works today even though nothing in the UI calls it yet.

### `server.ts` — the routes

| Route | Behavior |
|---|---|
| `GET /api/audio/:id` | `ensureCached(id)`, then streams the file (`res.sendFile`, which also handles HTTP Range requests automatically — so scrubbing the audio player's seek bar still works even though the file didn't exist a moment ago). |
| `DELETE /api/audio/:id` | Deletes the cached file if present — the "cache it until you say delete it" control. |
| `GET /api/cached-ids` | Lists which ids currently have a cached file, so the UI can show "cached ✓" vs. "will download on first play." |
| `POST /api/audio/:id/prefetch` | Calls `ensureCached` without streaming anything back — the unused-for-now prefetch infrastructure. |

`express.static(<apps/web/dist>)` is also mounted — but only when `NODE_ENV=production` (see Part 5.5 below for why). That means a friend can run `npm run build`, then `npm run start -w apps/api` (which sets `NODE_ENV=production` itself), and get the *entire* app — site and API — from one process on one port, rather than needing to explain two separate servers to someone who just wants to play the game.

## Part 5: wiring the two dev servers together

`apps/web` (Vite) and `apps/api` (Express) are two separate processes in development. Two small pieces connect them:

```ts
// apps/web/vite.config.ts
server: {
  strictPort: true,
  proxy: { "/api": "http://localhost:5174" },
},
```

The `proxy` entry means the browser can call same-origin `fetch("/api/audio/...")` and Vite quietly forwards it to the real API server — no CORS headers to think about. `strictPort: true` is a fix for a real bug hit while testing this: if port 5173 is already taken (e.g. a leftover dev server from an earlier session), Vite's default behavior is to silently try the next port — which, in this project, is 5174, the API server's own port. The proxy then pointed at itself, and every `/api/...` request failed with a `502`. `strictPort: true` makes Vite refuse to start at all if 5173 is taken, rather than silently drifting onto a port that breaks the proxy — a loud, immediate failure beats a confusing one three steps later.

```json
"dev": "concurrently -n web,api \"npm run dev -w apps/web\" \"npm run dev -w apps/api\""
```

`concurrently` runs both `npm run dev` commands in one terminal, labeling each line's output `[web]`/`[api]` so you can tell them apart — so `npm run dev` from the repo root remains one command, same as Phase 1, even though two separate processes are now involved.

### Part 5.5: a second port-related bug, found by actually hitting the wrong port

During testing, `apps/web/public/audio/` and `manifest.json` were deliberately deleted and regenerated a few times to confirm the "start empty, download on demand" behavior — and in the middle of that, the app started throwing `Couldn't load manifest.json (404 Not Found)` even though `manifest.json` visibly existed on disk at `apps/web/public/manifest.json`.

The cause wasn't a path bug at all — it was landing on the wrong port. `apps/api` (port `5174`) has that `express.static(<apps/web/dist>)` fallback described above, and back then it activated unconditionally whenever `apps/web/dist/` existed — with no check for *how stale* that build was. `apps/web/dist/` was a leftover build from testing `npm run build` earlier, made *before* the manifest workflow settled — so it had no `manifest.json` in it at all. Hitting `:5174` directly (easy to do by mistake — both `:5173` and `:5174` are legitimate-looking `localhost` URLs printed by `npm run dev`) served that stale, months-old build: the real API routes under `/api/...` worked fine (those are always live), but the page shell was frozen and missing the file entirely — a confusing, inconsistent mix that looked like a path bug but wasn't one.

The fix is the `NODE_ENV` check already shown in Part 4: `apps/web/dist` should only ever be served during an intentional production run (`npm run start -w apps/api`, which sets `NODE_ENV=production` itself), never silently during `npm run dev`. With that in place, hitting `:5174`'s root path during dev now correctly 404s instead of serving something stale — a clear, honest signal you're on the wrong port, rather than a confusing partial success.

This is also why `apps/web/dist/` and `apps/api/dist/` (both git-ignored build output, regenerated by `npm run build`) were deleted as part of this cleanup — stale build output sitting around during dev is exactly the trap that caused this bug, so the repo now starts with neither present, and each is only ever a fresh `npm run build` away.

## Part 6: `apps/web/src/App.tsx` — the small UI changes

The manifest fetch is untouched — `fetch("/manifest.json")` still works exactly as in Phase 1, because it's still a static file written by `npm run scrape`. What's new:

```tsx
function audioSrc(song: SongManifest["songs"][number]): string {
  return song.audio.kind === "local-file"
    ? song.audio.ref
    : `/api/audio/${song.id}`;
}
```

For a `"local-file"` song, the `<audio>` element points straight at the static file, exactly like Phase 1. For an `"embedded-link"` song, it points at the API's caching route instead — the browser doesn't know or care that the first request to that URL might take several seconds while a download happens server-side; it just sees an HTTP response eventually arrive, same as any other audio URL.

```tsx
const [cachedIds, setCachedIds] = useState<Set<string>>(new Set());
```

A `Set` (a built-in JS collection of unique values) fetched from `GET /api/cached-ids`, used only to decide what label/button to show — "cached ✓" plus a remove button, or "will download on first play." Refetched after every delete and after every `<audio>` `onPlay` event, so the label catches up once a download actually finishes.

This is also a nice payoff from Phase 0's original type design: `AudioKind = "local-file" | "embedded-link"` was defined back then and sat completely unused through all of Phase 1 — it's exactly the shape this phase needed, with zero changes to `packages/shared`.

## How to add songs (your day-to-day reference)

1. Add a row to `tools/scraper/data/songs.csv`: `<artist>,<title>,<year>`. That's it — no id, no link.
2. `npm run scrape` — resolves any new rows automatically (watch the console for a low-confidence warning) and regenerates `manifest.json`.
3. `npm run dev` — starts both the web and api servers. Open the printed `localhost` URL; new songs show "will download on first play," and start caching the moment you click play.
4. If a resolved match turns out to be wrong for some song, download the correct clip by hand (same `yt-dlp` command as Phase 1) to `apps/web/public/audio/<the-song's-derived-id>.mp3` — that silently overrides the automated resolver for just that song, forever (until you remove the file).

One-time setup this phase adds: a working `yt-dlp` install new enough to handle YouTube's current signature challenge (`.venv/bin/pip install -U yt-dlp` into a `python3 -m venv .venv` at the repo root is what this project itself uses), and — only on the machine actually running `apps/api` — a logged-in browser for `--cookies-from-browser` to borrow from (override which one via `YTDLP_COOKIES_BROWSER=<browser>` if it isn't Firefox).

`apps/api/data/cache/` (the downloaded mp3s) is git-ignored, same reasoning as Phase 1's `apps/web/public/audio/` — fully regenerable, this time automatically, on demand, per song, the first time it's actually played.

## What's next

The prefetch infrastructure (`ensureCached`, and the `/api/audio/:id/prefetch` route that calls it) is already built and working — it's just not called by anything yet. The natural next step is the timeline-guessing game logic itself; once that logic knows which song is coming up next, having it fire a `POST /api/audio/:next-id/prefetch` call as soon as the current song starts playing turns into a small, contained addition rather than new infrastructure — smoother playback with no gap for a download, without having designed anything differently today to make room for it later.
